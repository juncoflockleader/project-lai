## 魔女迷宫：一次正面的规格冲突

这是目前唯一一次「原作的做法被规格整条禁掉」。原作迷宫靠拼贴：剪纸、
混合材质、手绘涂鸦、透明叠加。`niulai.toml` 禁的正好是这些 ——
没有贴图、没有透明、没有体积、没有辉光。

规格里剩下的能做另一种迷宫：

| 手段 | 做法 |
|---|---|
| 配色发错 | 天暗紫、地深洋红，和正常世界的草绿蓝灰完全岔开 |
| 机械重复 | 28 个一模一样的葫芦排成阵列，全睁着眼 |
| 尺度错乱 | 一个 5.8 倍的葫芦悬在空中，人在底下 |
| 零件拼错 | 身子是歪方块、头是葫芦且和身子不接、肢是随便插的尖锥 |

**「一份建模到处粘」在这里不是省钱，是恐怖。** 这条原本是成本手段，
放进迷宫就变成了压迫感 —— 同一个资产复制 28 份，比 28 个不同的东西更难受。

新增原语只有一个：`spike`（低段数圆锥），牙、刺、塔尖都用它。

## 两千八百个葫芦：实测

科长问「能渲染两千八百个葫芦吗」。能，而且几乎不要钱。实测：

| | |
|---|---|
| 物体数 | 2802 |
| **不同网格** | **3**（葫芦、粉的、地面）|
| 总面数 | 381,099 |
| 建场景 | 3.3 秒 |
| 施加画质规格 | 0.2 秒 |
| 渲 121 帧 | 11.6 秒 |

**关键是那个 3。** 逐个走 `build_subject` 的话，每个葫芦要 `primitive_add` ×6
再加 `join` 和 `origin_set`，2800 个就是上万次 bpy.ops，会卡到没法用。
`build_array()` 建**一份**网格，然后 `obj.copy()` 出 2800 个对象引用共享它 ——
代价基本只有对象本身。

渲染时间和普通镜头（10 秒上下）没有区别：EEVEE 一次采样、平涂、无贴图，
面数根本不是瓶颈。

错位量用序号的整数哈希算，不用随机数 —— 同一份分镜渲两遍必须一模一样，
这条和画面的要求一致。

**这是 model once paste everywhere 的极限形态。** 同一条原则走完了三程：
省钱（一份葫芦供十五个）→ 恐怖（28 个一模一样的排成阵列）→
规模（2800 个几乎白送）。

## 穹顶与喷火：一次被实测推翻的判断

科长要三样：葫芦换成多色、从地面阵列改成天上的穹顶、随机几个喷火，
并叮嘱「喷火可能比较费经费，我们得悠着点」。

我当时同意了这个判断，理由是：葫芦能共享网格所以白送，
但每束火要单独的物体和关键帧，数量直接换时间。**实测把这个判断推翻了：**

| 火的数量 | 建场景 | 物体 | 网格 | 面 |
|---|---|---|---|---|
| 0 | 2.1s | 1802 | 9 | 245,099 |
| 60 | 2.4s | 1862 | 10 | 246,659 |
| 200 | 2.6s | 2002 | 10 | 250,299 |

200 束火只比 0 束多 **0.5 秒**，约 2.5 毫秒一束。不用悠着。

便宜的原因是实现的时候顺手把火也共享了：**一份火的网格 + 一份材质**，
只有位置和缩放关键帧是各自的。真正贵的写法是给每束火单独的动画材质 ——
角色用的 `apply_spray` 就是那样，那个才是数量换时间。

多色的做法：材质挂在网格上，链接复制没法各染各的，所以**几种颜色就建几份网格**，
实例在这几份之间轮着用。七色 = 七份网格，仍是常数级。

穹顶用斐波那契半球铺点，算出来的不是随机的，同一份分镜渲两遍一模一样。

还有一条：**穹顶上的东西要朝里，不是朝外。** 第一版 `face_out` 把葫芦的顶
对准径向朝外，站在底下看到的全是屁股。葫芦的脸在 −Y，所以正确做法是把
**+Y** 对准径向朝外，−Y 自然朝圆心。现在是 `orient: in / out / up` 三选一。

**顺带记一条镜头约定**（这次栽了一回）：`rot` 的 X 分量 **90 是水平，
大于 90 才是仰视，小于 90 是俯视**。给穹顶配了 58，拍了一地影子。
另外仰角也不能给太满：拍满一屏葫芦反而看不出是穹顶，
得留出地平线和人当参照，101 度才对。

## 一条更正

上一版曾断言葫芦兄弟片头「场景检测一个切点都没检出」。那是**测量方法坏了**：
`ffmpeg -v error` 会把 `showinfo` 的 INFO 级输出整个吞掉，任何片子都返回零。
改用 `metadata=print` 之后，圆来片头检出 52 个切点。零结果要先怀疑方法。
